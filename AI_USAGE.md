# Использование ИИ

## Инструменты и делегированные задачи

Использован CLI-инструмент opencode (модель big-pickle). ИИ вёл задачу
целиком: разбор задания, воспроизведение трёх проблем на локально
поднятом стенде, исправление бэкенда и фронтенда, написание автоматических
проверок (`tools/check.py`, `frontend/test/`), запуск проверок и заполнение
этого файла с `SOLUTION.md`. История чатов не прилагается — по условию
достаточно одного существенного примера.

## Один существенный пример

Задача, контекст и ограничения, которые вы дали модели:

«Исправь проблему быстрого переключения заявок: при клике по заявке 101
(отвечает ~1100 мс) и затем по 102 (~100 мс) карточка показывает данные
101. Ответ сохранения предыдущей заявки тоже не должен подменять текущую
карточку, но список заявок после сохранения должен обновиться. Работать
при включённых и выключенных задержках API, стек не менять, задержки
не убирать, изменения сделать минимальным диффом в TicketPanel.jsx.»

Существенный запрос либо его точное смысловое содержание:

«В TicketPanel нет защиты от устаревших ответов: ни эффект загрузки, ни
save() не знают, что заявка уже другая. Нужен способ применять ответ только
к актуальной карточке и отбрасывать запоздавшие ответы загрузки.»

Предложение модели и соответствующее изменение в коде:

- в эффекте загрузки — флаг отмены `active`: в `return () => { active = false; }`,
  все `then/catch/finally` проверяют флаг; заодно карточка очищается при
  переключении, чтобы ошибка не показывалась поверх прежней заявки;
- в `save()` — `const id = ticket.id` на момент запроса и `displayedIdRef`
  (ref, синхронно обновляемый во время рендера при смене `selectedId`):
  после ответа `if (displayedIdRef.current !== id) return` не даёт ответу
  подменить карточку, а `onChanged(data.ticket)` вызывается до этой
  проверки, чтобы список обновился в любом случае.
- в `api()` — аккуратная ошибка вместо `SyntaxError`, если ответ не JSON.

Изменение применено в `frontend/src/TicketPanel.jsx` и
`frontend/src/api.js`.

## Проверка результата

Что проверили самостоятельно и каким способом?

- Написан тест `frontend/test/race.test.mjs` (jsdom + esbuild + подменённый
  `fetch` с ручным порядком_resolve ответов): воспроизводит «101 → 102,
  ответ 101 опаздывает» и «сохранение 105 → переключение на 101, ответ
  сохранения опаздывает». Запуск: `cd frontend && npm test`.
- Тест прогонялся на исходном коде: оба сценария падали с реальным DOM
  («Заявка #101 Не работает интернет» вместо открытой #102; «Заявка #105»
  и «Источник сохранён» на карточке #101), после исправления — проходят.
- Для бэкенда написан `tools/check.py` (10 сценариев: права, архив,
  валидация, 401/403/400/404, порядок проверок, атомарность, история):
  на исходном коде падал 6 из 10, после исправлений — все 10, в том числе
  с `DEMO_LATENCY=1` и с выключенными задержками.
- Дополнительно: `tools/smoke.py` (PASS), `npm run build` (сборка PASS),
  ручные запросы к API через Python до/после (500 на заявке 103 и изменение
  источника зрителем — воспроизведены и устранены).

Что исправили или отклонили, если такое было?

- Отклонён `AbortController`: он отменил бы и ответ сохранения, который
  нужно применить, если заявка всё ещё открыта (и обновить список).
- Ошиблись с командой запуска тестов: `node --test test/` на Windows
  пытается выполнить каталог как модуль; заменено на глоб
  `test/*.test.mjs`. Тесты висели из-за живого event loop jsdom —
  добавлен `--test-force-exit`.
- Проверка порядка проверок (404 → 403 → 400) показала, что исходный код
  отдавал 400 до 404 — порядок исправлен в маршруте, а не только в тестах.
