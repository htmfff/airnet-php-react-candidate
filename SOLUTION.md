# Решение

## Затраченное время

Время разработки и отдельно время настройки окружения:

- Настройка окружения: ~30 минут. Docker на машине отсутствовал, поэтому
  для проверок локально были подняты PHP 7.4.33 (портативный архив
  windows.php.net), PostgreSQL 16.10 (binaries-архив EDB) и Python 3.12.
  На результат и стек это не повлияло: проверялся тот же PHP 7.4 + pgsql
  и та же схема БД, что и в `docker compose`.
- Разработка и проверки: ~50 минут (воспроизведение трёх проблем,
  исправления бэкенда и фронтенда, написание и отладка проверок).

## Найденные причины

### Проблема 1: при быстром переключении открываются данные предыдущей заявки

- Воспроизведение: карточка 101 отвечает ~1100 мс, остальные ~100 мс
  (`DEMO_LATENCY=1`). Клик по 101, затем по 102 — ответ 102 приходит
  раньше ответа 101. Второй сценарий: нажать «Сохранить» и тут же
  переключиться на другую заявку — ответ сохранения приходит позже.
- Причина: в `frontend/src/TicketPanel.jsx` эффект загрузки карточки не
  отслеживал отмену — запоздавший ответ `setTicket()` перезаписывал
  текущую заявку. Аналогично `save()` всегда применял ответ к состоянию,
  независимо от того, та ли заявка сейчас открыта.
- Исправление: флаг `active` в эффекте (устаревшие ответы и ошибки
  отбрасываются), карточка очищается при переключении; в `save()` id
  заявки запоминается на момент запроса и ответ применяется, только если
  она всё ещё выбрана (`displayedIdRef`, обновляемый во время рендера).
  Список обновляется в любом случае — изменение реально произошло.
- Проверка: `cd frontend && npm test` — оба теста падают на исходном
  `TicketPanel.jsx` (фактический вывод: карточка показывает «Заявка #101»
  вместо #102, и «Заявка #105» вместо открытой #101) и проходят после
  исправления.

### Проблема 2: карточка заявки без источника загружается с ошибкой

- Воспроизведение: `GET /api/tickets/103` (в заявке `source_id IS NULL`)
  возвращал 500 `internal_error`. Тест `tools/check.py` воспроизводит это
  на исходном коде.
- Причина: `TicketRepository::find()` безусловно делал
  `SELECT ... FROM sources WHERE id=$1` с `NULL` и обращался к результату
  `pg_fetch_assoc()`, который возвращает `false` при пустой выборке.
  Доступ к массиву по ключу на `false` поднимал `ErrorException`
  (обработчик ошибок в `bootstrap.php`) → 500.
- Исправление: источник запрашивается только если `source_id` не NULL,
  в JSON возвращается `source: null`; список уже отдавал
  `source_name: null`, а фронтенд отображает «Не указан».
- Проверка: сценарий «заявка без источника: 200 и source=null»
  в `tools/check.py` (падал → прошёл).

### Проблема 3: сотрудник только на просмотр смог изменить источник

- Воспроизведение: вход под ролью `viewer`, `POST /api/tickets/102/source`
  → 200, источник изменён, в истории появилась запись от «Анны Примеровой».
- Причина: в `backend/src/routes.php` у маршрута смены источника не было
  `requirePermission(..., 'FUNC_TICKETS_SOURCE_EDIT')` и не проверялся
  статус архивной заявки. Дополнительно порядок проверок был неверным:
  формат `source_id` проверялся до наличия заявки (400 вместо 404),
  архив не блокировался вовсе, повторный выбор источника добавлял лишнюю
  запись в историю, а `UPDATE` + `INSERT` шли без транзакции.
- Исправление в `routes.php` и `TicketRepository.php`:
  1. `requirePermission($employee, 'FUNC_TICKETS_SOURCE_EDIT')` — право
     берётся из серверной сессии, до всяких изменений данных;
  2. `changeableTicket($id)`: сначала 404 (заявки нет), затем 403
     (архивная), и только потом 400 (формат `source_id` и существование
     id в `sources`);
  3. тело запроса читается только как `source_id`: имя, id сотрудника и
     права из запроса игнорируются — в истории сотрудник из сессии;
  4. изменение и запись истории выполняются в одной транзакции
     (`BEGIN`/`COMMIT`, при сбое `ROLLBACK`);
  5. повторный выбор текущего источника возвращает 200 без новой записи
     истории.
- Проверка: сценарии «только просмотр», «архивная заявка», «порядок
  проверок», «некорректный источник», «успешное изменение» в
  `tools/check.py`.

## Решения и компромиссы

- Проверки оставлены в `routes.php`/`TicketRepository.php` без нового
  слоя middleware: проект маленький, стек — «чистый PHP 7.4», отдельный
  слой только размазал бы логику. Порядок проверок задан явно в маршруте
  и защищён повторной проверкой внутри `changeSource()`.
- Валидация `source_id` — руками (`is_int` + положительное число +
  существование в `sources`) вместо валидатора: требование покрывает
  пять случаев, библиотека здесь была бы тяжелее задачи.
- На фронтенде выбран флаг отмены вместо `AbortController`: ответ
  сохранения нужно не отбрасывать безусловно, а применить, если заявка
  всё ещё открыта, а отмена соединения этого не позволяет. `ref`
  обновляется во время рендера, поэтому ответ не может «проскочить»
  между кликом и запуском эффектов.
- `api()` научился корректно сообщать ошибку, если ответ не JSON: это
  не меняет контракт, но убирает случай `SyntaxError` вместо внятной
  ошибки на экране.
- Задержки API не трогались — проверки проходят и с `DEMO_LATENCY=1`,
  и без него (запускались в обоих режимах).

## Запуск проверок

Команды и фактические результаты:

```sh
# инфраструктура и базовые маршруты (поставляется с заданием)
python3 tools/smoke.py http://localhost:5173
#   PASS: PHP 7.4, isolated database, session, list, sources, normal ticket

# сценарии решения (10 проверок; на исходном коде падало 6)
python3 tools/check.py http://localhost:5173
#   ИТОГ: все 10 проверок пройдены   (запускалось дважды:
#   с DEMO_LATENCY=1 и с выключенными задержками — одинаковый результат)

# тесты гонок UI (2 проверки; на исходном коде падали обе)
cd frontend && npm test
#   pass 2, fail 0

# сборка фронтенда
cd frontend && npm run build
#   ✓ built in 311ms
```

Проверки API не зависят от текста сообщений и порядка ответов, опираются
только на HTTP-статусы, JSON и неизменность данных при отказах.
Перед запуском применялись `database/001_schema.sql`, `002_seed.sql`
и `database/reset.sql`.

## Одновременное редактирование

Что произойдёт при изменении одной заявки двумя сотрудниками сейчас:

- Оба запроса проходят независимо: каждый берёт текущий `source_id`,
  пишет `UPDATE` и свою строку истории в своей транзакции. Последняя
  запись побеждает — изменение первого сотрудника теряется как состояние.
- История при этом остаётся полной: в ней будут обе записи, но у второй
  `old_source_id` может не совпадать с `new_source_id` первой, если
  оба читали заявку до коммита друг друга.
- UI не показывает конфликт: оба сотрудника увидят «Источник сохранён»,
  и у каждого после перезагрузки окажется источник второго.
- В защите от такой потери изменений по условию не участвовал. Естественное
  развитие: проверка `updated_at` (или отдельной версии) в условии `UPDATE`
  и ответ 409 при расхождении с перечитыванием карточки.

## Оставшиеся ограничения

- `tools/check.py` рассчитан на свежую учебную БД (после `001+002` или
  `reset.sql`): сами проверки восстанавливают источники, но созданные ими
  записи истории не удаляются — API удаления истории не существует.
- Тесты UI (`npm test`) выполняются в jsdom: они покрывают обе гонки
  состояния, но не заменяют визуальную проверку в браузере (вручную
  в браузере не проверялось — на машине нет Docker/браузерной автоматизации).
- `docker compose up` вживую не запускался (Docker на машине
  разработчика отсутствовал); код и compose-конфигурация не менялись,
  локально проверялся тот же PHP 7.4 + PostgreSQL 16.
- На Windows не поддерживаются параллельные PHP workers встроенного
  сервера, поэтому одновременность запросов вживую проверялась только
  через тесты с контролируемым порядком ответов.
- Следующий шаг: 409 при одновременном редактировании и, при желании,
  e2e-тест в настоящем браузере (Playwright).
